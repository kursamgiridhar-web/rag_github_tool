# Implementation Plan — Cross-File Repository Investigator

> Living document. Any AI assistant (Claude Code, Antigravity, ...) should read this and `README.md` first, then continue from the phase marked **NEXT**.

## 1. Problem statement (hackathon Track 2: RAG Engine)

Build a RAG product over a focused collection of source material. Requirements from the brief:

- User can import a collection and see it become searchable.
- Retrieve evidence from **more than one source / distant sections**, then answer / investigate.
- **Show the source behind every important result** (exact passages).
- Handle **at least one difficult or unanswerable request** clearly.
- MongoDB: store sources, chunks, embeddings, metadata and source IDs together; use **MongoDB Vector Search**; add **metadata filters**; use **hybrid search** if exact names/keywords matter (they do in code); keep a **small eval set of questions + expected source IDs**.

Our choice: sources = files of a public GitHub repository. Users ask questions about the code.

## 2. Tech stack (fixed)

| Layer | Tech |
|---|---|
| Frontend | React (Vite) + plain CSS, dark theme |
| Backend | Node.js + Express |
| Repo access | GitHub REST API (public repos, no cloning, nothing is ever executed) |
| Storage + retrieval | MongoDB Atlas + Atlas Vector Search |
| Embeddings | Gemini embedding model (same API key as the LLM; model name in `.env`) |
| LLM | Gemini API (model name in `.env`) |

Backend uses ESM, plain `fetch`, the official `mongodb` driver and nothing else beyond `express`, `cors`, `dotenv`.

## 3. Architecture

```
React UI ──► Express API ──► ingestion ─► chunking ─► embeddings ─► MongoDB (chunks + vector index)
                       └──► retrieval (vector search + filters) ─► llm (Gemini) ─► answer + citations
```

Folder layout (created in Phase 1, filled as phases progress):

```
backend/
  src/
    server.js            Express entry
    config.js            env loading
    routes/              API routes (repos, ask)
    ingestion/           GitHub fetching + file filtering
    chunking/            line-aware code chunker
    embeddings/          Gemini embedding client
    db/                  MongoDB connection + collections + index setup
    retrieval/           vector search, filters, (later) hybrid + re-rank
    llm/                 Gemini answer generation + prompt
  eval/                  test questions + expected files (Phase 4)
frontend/
  src/                   React app (components/, lib/, api.js, styles/)
docs/IMPLEMENTATION_PLAN.md
README.md  .env.example  .gitignore
```

MongoDB collections: `repos` (one doc per import: url, status, counts) and `chunks` (repoId, filePath, language, startLine, endLine, text, embedding, createdAt).

## 4. Security rules (apply in every phase)

- Never execute, install or build imported code. Only read text over the GitHub API.
- Repo content is **untrusted data**: it goes into the prompt inside clearly delimited evidence blocks, and the system prompt tells Gemini to ignore any instructions found there.
- Skip binaries, lockfiles, `node_modules`, large files; cap file count and size.
- Secrets only in `.env` (git-ignored). Never log or return keys.
- Citations come only from retrieved chunk metadata, never generated by the LLM from memory.

## 5. Phases

Work one phase at a time. **Stop after each phase and wait for team verification.**

### Phase 1 — Basic Setup and UI  *(DONE — awaiting verification)*
- Repo skeleton, `.gitignore`, `.env.example`.
- Express server with `GET /api/health`, config loading.
- React app: repo URL input + Import button + status area, question box + Ask button, answer panel, evidence panel (dark theme). Calls placeholder endpoints.
- **Done when:** `npm run dev` for backend and frontend both start, UI renders, health check works, UI shows a clear "backend not implemented yet" state for import/ask.

### Phase 2 — Repository Processing
- `POST /api/repos` parses a GitHub URL, lists files via the GitHub tree API, filters (extensions, size, ignored dirs), downloads contents.
- Line-aware chunker (~40–60 lines, small overlap) keeping `filePath`, `startLine`, `endLine`.
- Return chunk stats; chunks held in memory/temp output (embedding comes next).
- **Done when:** importing a small public repo returns a file list and chunks with correct paths and line ranges.

### Phase 3 — Basic RAG Pipeline  → **first working MVP**
- Gemini embeddings for chunks; store in MongoDB Atlas `chunks` with metadata; `repos` status tracking (indexing → ready / failed).
- Create Atlas Vector Search index (with `repoId` as filter field); retrieve top-k with `$vectorSearch` filtered by repo.
- Gemini answers from retrieved chunks only; response = answer + citations (file, line range, snippet).
- UI shows answer + evidence panel; basic error handling.
- **Done when:** end-to-end import → ask → cited answer works on a small repo.

### Phase 4 — Improve Retrieval and Answers
- Hybrid search: Atlas Search text index + vector search merged (exact identifiers like `MONGO_URI`, function names).
- Metadata filters (file type / path prefix); multi-file evidence: retrieve broadly, ensure diversity across files, include config/test files for bug questions.
- Prompt for **Feature 1 (trace a feature)**, **Feature 2 (investigate a bug)**.
- **Feature 3 (missing evidence):** relevance-score threshold + prompt rule so the app says "not found in this repository" instead of guessing.
- Citation check: drop any citation not in the retrieved set.
- Eval set: ~8–10 questions with expected files in `backend/eval/`, plus a script printing hit/miss.

### Phase 5 — Final Features and Demo
- UI polish (indexing progress, clickable citations, code highlighting), loading/error states.
- Full test pass, demo repo chosen, 3–4 scripted demo scenarios (trace, bug, unanswerable, multi-file).
- Final README, known issues, PPT screenshots.

## 6. Demo flow (maps to the judging brief)
1. Import a small repo → shows indexing status → searchable.
2. Trace question needing frontend + backend + DB files → answer cites multiple files.
3. Open evidence panel → exact code lines shown.
4. Ask something absent from the repo → app says it can't find evidence.
